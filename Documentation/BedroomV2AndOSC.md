## 本轮玩法

只从卧室开始，玄关保留场景但不参与本轮流程。固定相机 `(815,1070,100)`，地板约 Z=-79，相当于离地 179；水平视野 118°，初始仰角 8°，HOME 回正。右键拖动环视，不能移动。左键选择墙面/碎片或底部按钮；1–5 选面，Q/E 转动 90°，空格确认拼合，H 提示，Z 撤销，R 重置，F3 显隐通信信息。

物件保留原始尺寸，不在拼合或成功提示时放大缩小。移除了按 actor 原点距离把碎片隐藏的逻辑；旧逻辑无法反映网格真正位置，还会在拼合动画开始时把碎片直接隐藏。成功仍有金色高亮与环形提示，取消镜头 FOV 突变。

| 对象 | 目标角度（其他面不限） | 完成行为 |
|---|---|---|
| 床 | B=90、C=270、E=180 | 回到侧边地面，避开中央视点 |
| 柜子 | A=180、E=90 | 回到原柜子位置 |
| 桌子 | C=180、D=90、E=270 | 回到原桌子位置 |
| 窗户和窗框 | A=270、D=180、E=90 | 玻璃、窗框、窗台归位；继续随 D 墙旋转 |

无需按表格顺序完成。床、柜子、桌子完成后不再被打乱。窗户是建筑附件，需跟随带窗洞的墙，以免窗框与洞口错位。所有对象完成后恢复墙体初始姿态。窗框增加四个碎片，各自通过 `RH_HOME_<原Actor名>` 找到正确归位变换，避免全部被压到玻璃的变换与比例。`RH_FOLLOW_FACE_3` 标记窗户附属结构。修改名称时保留此引用或同步更新标签。

两盏卧室补光已移回室内/调整朝向。当前房间真实右边界约 X=1480，旧位置 X=1640 位于墙外。现有第三方 Infinity 材质有 NULL 纹理编译警告，可能显示默认材质；本轮没有替换全部第三方材质。

## 现有 OSC 实际情况

目前路线是 **ESP32 → Wi-Fi OSC/UDP 8000 → Python osc_bridge.py → 本机 JSON/UDP 19872 → HallwayPuzzle**。Unreal C++ 的 19872 端口不是原生 OSC 解码器。不要把 OSC 二进制直接发到 19872，也不要同时启动两个占用 8000 的接收器。

项目有两种固件协议：

- `Arduino/new_rotate/new_rotate.ino` 等旧版：`/rotary` 五个角度，`/imu` 四个原始值；桥接将初始编码器值映射到游戏当前角度，支持五面同时连续更新。原始 BNO Euler 的 X/Y/Z 在旧代码中按 heading/roll/pitch 解释，不能只看变量名字。
- `roomshift_oct30a_copy_20261030144511/roomshift_oct30a_copy_20261030144511.ino`：`/rotate` 的参数为字符串 A–E 和 int32 ±1；`/view` 为三个 float，相对 yaw/pitch/roll；`/shake` 无参数。默认不发原始 `/imu`。原桥接不识别 `/rotate` 和 `/view`，本轮已补齐。此版本是 90° 事件，不能凭这些消息恢复不足 90° 的物理角度。

新 `/view` 使用固件已算好的相对 yaw/pitch，不重复把它当每帧增量；roll 暂不用于镜头倾斜。反向可用 `--yaw-gain -1` 或 `--pitch-gain -1`。固件 `VIEW_ZERO` 用于重设实体姿态零点。当前地图 A 是门洞侧墙、D 是窗洞侧墙；HUD 的 FRONT/BACK 沿用旧命名，接线以 A–E 编号为准。

当前桥接对 `/rotate` 做有界队列，动画完成后再执行下一次；排队超过 2 秒丢弃并打印提示，避免旧操作过很久才重放。这是兼容原型，不是多个面同时连续动画的最终实现。既有 `/rotary` 路径一次更新五面，适合最终同步方案。

`/shake` 目前确认已经对齐的物件并播放归位，不会随机打散已完成家具。文件“控制器描述”中写的任意已拼好物体掉落，与现有玩法实现不同。若要支持自由物理掉落，应另定义 drop 动作，不能悄悄把 assemble 改成物理模拟。

## 下次实物测试步骤

1. 双击工程，打开 Hallyway1，点 Play。先用鼠标/Q/E/空格完成柜子，确认游戏本身正常，再按 R 重置。
2. 明确板上实际烧录哪一份草图。串口显示传感器数字只证明采集正常，还要确认 Wi-Fi 已连接和发送目标 IP。保留现有可工作的固件，不要求为了启动桥接而重新烧录。
3. 电脑与 ESP32 同一热点；用 `ipconfig` 查电脑 Wi-Fi IPv4。固件的 laptopIP 必须是该地址，端口 8000。若地址变化才改相应配置。Windows 入站防火墙需允许 Python 的 UDP 8000。
4. PowerShell 执行：

```powershell
cd 'D:\DKU_Academic\junior session1\AtrlCtrl Workshop\RoomShiftDemo'
python Tools\osc_bridge.py
```

5. 观察 `OSC link online: first packet from ...`。应来自 ESP32 的局域网 IP，不能把 127.0.0.1 本机测试数据当作硬件接入成功。新固件转面应出现 `/rotate`，转盒子应出现 `/view`；旧固件对应 `/rotary` 和 `/imu`。F3 可在游戏中查看。
6. 新固件如果没有 `/rotate`，先确认 CPR 校准与 PLAY 模式：串口输入 CAL，每个面各转完整一圈，记录各自 COUNT，输入 `CPR,nA,nB,nC,nD,nE`（实际测得计数，不猜测），对齐物理零位后执行 ZERO（以固件实际支持命令为准）、PLAY；静止握好盒子后 VIEW_ZERO。CPR 为零时不进入有效旋转检测。不要把半正交版本的 CPR 数直接套到新四倍计数版本。
7. 先测试一个面正/反各 90°，记录 A–E 与游戏墙的对应与方向；再测试两个面；最后测试姿态与摇晃。当前游戏 A/B/C/D/E 是固定编号，固件注释的 BACK/BOTTOM 不是自动检测方位。必要时调整映射，不用改房间模型。

可用 `python Tools/device_bridge.py --status` 单独检查 Unreal 本机端。这条命令不证明 ESP32 到电脑成功。

## 后续推荐架构

保持 OSC，逐步改为：ESP32 每 20–33ms 发送五面**绝对角度**快照、独立姿态、带事件序号的 shake。五个绝对值同一消息保证多个面同时转动；UDP 丢一包可由下一包恢复，避免累加事件永久不同步。消息增加递增序号和发送时间；明确 A–E 排列、方向和计数标定。

接收端后台收包只保留最新快照，Unreal 每帧读取最新状态并更新各面；不对每一个连续样本同步等待 ACK。控制面可加轻量插值，停止后满足 ±5°、稳定 0.2 秒再允许确认。reset/center/assemble 等事件单独使用序号、确认和去重。失联超过 0.5 秒保持最后姿态并提示，不补播积压旋转。鼠标与 IMU 需明确控制优先级：建议按住右键时鼠标优先，松开后重新标定相对偏移，避免两者争抢镜头。

可继续用 Python 作为调试网关，或迁入 Unreal 的独立 OSC 接收模块；两种方案都不要在游戏线程等待网络 ACK。目前桥接仍有同步等待，不能声称延迟已完全解决。编辑器失焦时会限帧；本轮日志曾显示 max tick rate 3，约一帧333ms，足以解释先前270–370ms的部分本地延迟。实测时关闭 Editor Preferences 的 Use Less CPU when in Background，或用独立游戏窗口/打包程序测量；这不解决未收到 Wi-Fi 包的问题。

当前固件未实现接收马达指令；有 UDP localPort 不等于已经能处理反馈。后续约定 `/feedback/haptic <事件序号> <时长ms> <强度>`，ESP32 增加收包与去重，实际电机经驱动电路供电。现有 Unreal 普通手柄 ForceFeedback 也不会自动驱动 ESP32。

## 推荐房间布局

中央保留固定观察区，所有完整家具靠周边；床沿一侧、柜子放对角、桌子在另一侧，窗户高于桌子。三个大物件不要并排挡住一个方向。当前房间宽约13米、高约8.6米且床很大，属于放大的原型尺度；未来最好统一场景比例后重新切分，不在游戏中动态缩放。建议柜子两片入门、桌子三片进阶、床三片跨左右与顶面、窗框作为明显的最终建筑目标。分阶段引导注意力，但允许玩家选择完成顺序；保留明显的边缘/纹理连接线，降低纯透明玻璃的辨识难度。
